# 🗄️ Day 67: Docker Volumes & Data Persistence

## 📋 Project Overview
By design, Docker containers are ephemeral. If a container is destroyed, all data written inside its writable layer is permanently lost. This is catastrophic for stateful applications like Databases. Today, I engineered a highly resilient architecture by implementing **Docker Volumes** to decouple data storage from the container lifecycle.

## ⚙️ Core Concepts Explored
* **Ephemeral Nature of Containers:** Understanding why data should never be stored directly inside a container's filesystem.
* **Docker Volumes:** The preferred mechanism for persisting data generated by and used by Docker containers. Volumes are fully managed by Docker and isolated from the core functionality of the host machine.
* **Volume Mounting (`-v`):** Bridging a secure volume on the host directly into a specific directory inside the container (e.g., `/var/lib/mysql`).
* **Interactive Exec (`docker exec`):** Spawning a secondary process inside a running container to interact with its internal CLI.

## 🛠️ Execution Steps
1. **Volume Provisioning:** Created a secure storage vault using `docker volume create day67-mysql-data`.
2. **Stateful Deployment:** Deployed an official `mysql:8.0` container, injecting a root password via environment variables (`-e`) and attaching the newly created volume to MySQL's default data directory.
3. **Data Generation:** Executed an interactive bash session (`docker exec -it`) into the MySQL shell and manually created a database named `devops_company`.
4. **Disaster Simulation:** Force-deleted the database container (`docker rm -f`) to simulate a critical server failure.
5. **Recovery & Validation:** Spun up a brand new MySQL container, mapped it to the *same* Docker Volume, and successfully verified that the `devops_company` database persisted flawlessly.
